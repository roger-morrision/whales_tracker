# Job 3 — Product Owner Review and Phased Enhancement Roadmap

**Run date:** 2026-08-16  
**Inputs:** Job 1 QC/QA audit, Job 2 UI/UX audit, and static review of the product source.  
**Decision:** **Stabilize trust and navigation before adding net-new breadth.** The repository already exposes a broad terminal (discovery, whale activity, signals, leaderboard/profile, search, alerts, wallet and trading tools), but broken route/control contracts make additional feature expansion counterproductive.

## Product outcome and guardrails

**Primary outcome:** help a user discover credible smart-money activity, understand why it matters, and watch/follow it without losing context.

**Guardrails for Job 4:**

- Do not autonomously alter wallet signing, transaction execution, secrets, environment files, database migrations, or market-data provenance.
- Do not present mock/shuffled data as refreshed live data.
- Route, visible heading, selected navigation and browser history must agree.
- Every apparent control must either work or be removed/disabled with honest explanatory copy.
- Instrument outcomes without recording wallet addresses, search content or other identifiers in analytics payloads.

## Prioritization model

- **P0:** trust, correctness, navigation, release blockers.
- **P1:** core workflow completion, mobile usability and accessibility.
- **P2:** retention and decision support after foundations are measurable.
- Effort is a relative engineering estimate: **S** (≤2 developer-days), **M** (3–5), **L** (1–2 weeks), excluding external API/compliance work.

## NOW — reliability and coherent core journey (release gate; 1–2 sprints)

### N1 — Canonical route registry and URL-owned navigation — P0 / M

**User value:** every deep link, reload, Back/Forward action and navigation highlight is predictable.  
**Scope:** choose one canonical label/URL per destination; repair `/whales` and `/portfolio` aliases; replace direct `setActiveTab` transitions with links/router navigation; expose Signals on mobile through a fifth item or a tested four-plus-More model.  
**Dependencies:** product naming decision (recommended: **Discover**, **Whale Activity**, **Signals**, **Leaderboard**, **Profile**; treat Portfolio as a distinct future wallet-owned view or redirect the legacy alias).  
**Acceptance criteria:**

- Route matrix covers `/`, `/feeds` (or the chosen whale route), `/signals`, `/leaderboard`, `/profile`, and legacy redirects.
- URL, page heading, content, document title and `aria-current` agree at 320, 768, 1024 and 1440 px.
- Every in-product entry point supports reload, Back/Forward and open-in-new-tab.
- No component can create a primary tab state that disagrees with the pathname.

**Success metrics:** route-mismatch error rate = 0 in E2E; primary-navigation dead ends = 0; ≥99.9% successful canonical route renders.

### N2 — Make filters, reset and refresh honest and functional — P0 / L

**User value:** users can narrow activity and trust that refresh actually checks the source.  
**Scope:** implement typed filter state (transaction type, wallet class, period, sort), mobile filter sheet/desktop panel, applied count/removable summary, Apply/Clear, zero-result recovery; connect refresh to the actual data-hook refetch rather than mock shuffling.  
**Dependencies:** agreed query/filter contract and API capabilities; preserve client-side fallback only when labeled.  
**Acceptance criteria:**

- Every visible filter changes selected state and results/query; Clear is disabled at defaults.
- Applying filters persists through the URL where shareability matters and survives refresh.
- Refresh issues a second request, preserves old content while refreshing, updates freshness/provenance, and reports failure without claiming success.
- Loading, initial error, stale error, genuine empty and filtered-empty have distinct copy and actions.

**Success metrics:** filter apply-to-result success ≥99%; refresh request success and latency dashboards established; zero false-success toasts; filtered-empty recovery click rate tracked.

### N3 — Semantic interactions and deterministic regression coverage — P0 / M

**User value:** keyboard, switch, screen-reader and automation users can open traders and operate controls.  
**Scope:** replace clickable trader/card containers with semantic links/buttons, isolate Follow from detail navigation, correct the impossible E2E selector, add stable accessible names and focus styles, audit similar card patterns.  
**Dependencies:** N1 route-backed detail target.  
**Acceptance criteria:**

- Trader detail and Follow are separate Tab stops; Enter/Space activates only the intended action.
- E2E uses roles/names where possible and passes without selectors absent from production.
- Automated axe scans cover canonical views and representative cards; no serious/critical violations.
- Primary touch targets are at least 44×44 CSS px or equivalently spaced.

**Success metrics:** core keyboard task completion 100%; serious/critical axe issues = 0; flaky E2E retry rate <1%.

### N4 — Unified search and compact mobile header — P1 / M

**User value:** search once across tokens, contracts, wallets and traders without a cramped phone header.  
**Scope:** one controlled search query; icon trigger/full-height command sheet on phones and optional inline field on larger screens; group result types; deterministic clear/Escape/reopen; put long-tail tools behind a named Tools/More surface.  
**Dependencies:** search result contract and route-backed details from N1.  
**Acceptance criteria:**

- One typing action populates results; selecting and returning preserves useful query context.
- At 320 px and 200% text zoom, header has no collision/document overflow.
- Search/clear controls have names, visible focus and 44 px targets.
- Hidden phone tools remain reachable within two actions.

**Success metrics:** median search-to-detail ≤2 actions; search abandonment and zero-result rate instrumented; duplicate-query defect = 0.

### N5 — CI/test environment repair as a release prerequisite — P0 / M

**User value:** regressions are caught before deployment.  
**Scope:** resolve the existing Vite/React plugin dependency conflict, install dependencies reproducibly, and run lint, unit/contracts, build and Playwright route/task smoke tests.  
**Dependencies:** maintainer approval for lockfile changes; provisioned browser environment.  
**Acceptance criteria:** clean checkout succeeds with one documented install command; lint, unit/contracts, build and core E2E all pass; failures cannot be classified as release-ready.

**Success metrics:** main-branch required-check pass rate ≥95%; median repair time <1 business day; core E2E flake <1%.

## NEXT — retention-quality workflow and responsive consolidation (2–4 sprints)

### X1 — Route-backed trader/token detail and investigation flow — P1 / L

**Pattern to adapt:** preserve a scan/list while opening an inspectable detail context, common in market terminals; do not duplicate a competitor’s visual treatment.  
**Scope:** shareable detail URL rendered as mobile sheet and desktop side pane; source, timestamp, freshness, risk context; Watch/Follow as primary action; restore list filters/scroll on Back.  
**Dependencies:** N1, N2, N3; data/provenance fields.  
**Acceptance criteria:** detail in ≤2 actions, Follow/Watch in ≤3; URL is shareable; Back restores exact list state; one Escape closes one conceptual level.  
**Metrics:** detail-open rate, watch/follow conversion, median time to context, Back-state restoration errors.

### X2 — Alerts as a closed-loop workflow — P1 / L

**Pattern to adapt:** configurable price/activity alerts and watchlists found across crypto screeners and analytics tools.  
**Scope:** create alert from followed trader/token; threshold/activity type, channel and cooldown; inbox deep-links to evidence; pause/delete/test; transparent delivery status. Avoid implementing notification delivery until backend and consent contracts exist.  
**Dependencies:** authenticated identity/consent decision, delivery service, X1, privacy/security review.  
**Acceptance criteria:** create/edit/pause/delete with clear validation; alert links to the triggering entity/event and timestamp; deduplication/cooldown tested; permission denial has recovery guidance.  
**Metrics:** alert setup completion, actionable-alert open rate, duplicate/false alert rate, opt-out rate.

### X3 — Responsive component and overlay system — P1 / L

**Scope:** standardized Dialog/Drawer primitives with `dvh`, safe-area padding, focus trap/return and overlay stack; reflow four-column stats to two columns on narrow phones; semantic tablists with visible overflow affordance; reduced-motion coverage.  
**Dependencies:** N3; shared design-token decisions.  
**Acceptance criteria:** viewport matrix from Job 2 passes with no page overflow/obscured actions; keyboard remains visible with fields; only top overlay closes; 200% zoom and reduced motion retain information.  
**Metrics:** mobile usability defects per release, axe score, overlay escape/focus regression count, Core Web Vitals segmented by viewport.

### X4 — Decision-quality smart-money explanations — P1 / L

**Pattern to adapt:** labeled wallet/entity context and transparent signal evidence used by wallet-intelligence products.  
**Scope:** explain smart score inputs, label provenance/confidence, realized vs unrealized PnL, timeframe, sample size, freshness and “why surfaced”; never imply certainty or financial advice.  
**Dependencies:** validated scoring methodology and data lineage; legal/compliance review.  
**Acceptance criteria:** every score has an explanation and timestamp; unknown/low-confidence labels are explicit; metrics use consistent definitions/timeframes; source outage produces stale/error state, not fabricated continuity.  
**Metrics:** explanation-open rate, reduced “what does this mean?” support contacts, stale-data exposure rate, user trust survey.

### X5 — Intent-based onboarding and saved workspace — P2 / M

**Scope:** optional choose-chain → watch wallet/topic → select interests/risk → populated feed; skip/browse without wallet; save selected filters/watchlists.  
**Dependencies:** N1/N2, persistence/privacy decision.  
**Acceptance criteria:** relevant whale activity in ≤3 decisions; Back/Skip/resume work; wallet connection is optional; defaults produce useful content.  
**Metrics:** onboarding completion, time to first useful activity, first-session follow/watch rate, D1/D7 return.

## LATER — differentiated intelligence after trust is proven (quarterly discovery)

### L1 — Entity graph and transaction-flow investigation — P2 / XL

**Pattern to adapt:** graph-based wallet/entity exploration associated with blockchain-intelligence products.  
**Discovery first:** validate whether target users need fund-flow investigations versus faster feeds. Prototype graph + timeline with progressive loading; do not ship an unreadable mobile graph.  
**Dependencies:** entity clustering methodology, high-volume graph backend, confidence/provenance model, compliance review.  
**Exit criteria:** ≥5 target-user interviews; ≥70% complete a defined source-to-destination task in prototype; performance budget and false-link review approved.  
**Metrics:** investigation completion time, useful-path saves/shares, disputed entity-link rate.

### L2 — Comparative wallet/trader cohorts and custom dashboards — P2 / XL

**Pattern to adapt:** cohort labels, saved dashboards and wallet portfolio views used by analytics products.  
**Scope:** compare a small number of wallets across consistent periods; saved modules; exports only with clear timestamps and definitions.  
**Dependencies:** metric definitions, persistence, entitlement model and scalable aggregation.  
**Exit criteria:** users can reproduce displayed numbers from documented definitions; dashboard mobile fallback is a prioritized card list, not a squeezed grid.  
**Metrics:** saved-dashboard weekly use, cohort-to-follow conversion, export success, metric dispute rate.

### L3 — Explainable signal ranking and feedback loop — P2 / XL

**Scope:** ranking based on explicit, versioned features with “why shown,” mute/not useful feedback and offline evaluation. No opaque performance promises.  
**Dependencies:** sufficient labeled outcomes, model governance, bias/leakage review, rollback and monitoring.  
**Exit criteria:** benchmark beats a simple chronological baseline on agreed precision/recall; explanations pass comprehension tests; ranking can be disabled independently.  
**Metrics:** precision at K, alert usefulness feedback, calibration, hide/mute rate, drift.

### L4 — Multi-chain expansion — P2 / XL

**Scope:** expand only after chain-specific parity contracts cover addresses, decimals, routing, sources and freshness.  
**Dependencies:** reliable providers, chain abstraction, security review, per-chain QA fixtures.  
**Exit criteria:** no cross-chain address ambiguity, chain always visible, source/freshness parity documented, performance within budget.  
**Metrics:** active users and retained watchlists per chain, data error rate per chain, provider latency/availability.

### Verification checklist for the next PO research pass

1. Open each official product and documentation page; capture access date, platform/version and direct feature documentation URL.
2. Validate each hypothesis hands-on at phone and desktop widths; distinguish free, authenticated and paid behavior.
3. Record task steps for: find trader, inspect evidence, follow/watch, set alert, return to prior filters.
4. Compare information architecture, state/error honesty, accessibility and data provenance—not colors or surface styling.
5. Test at least three target users on our prototype; competitor presence alone is not evidence of user value.

## Sequenced backlog handed to Job 4

Job 4 should implement only the safe, repository-contained **NOW** slice in this order:

1. **N1 canonical routes/navigation**, including legacy redirects and route matrix tests.
2. **N3 semantic trader interactions and the broken E2E contract** (can land with N1).
3. **N2 functional filters and true refetch/status state machine**, behind tests and without inventing backend capabilities.
4. **N4 unified search/mobile header** after navigation and state contracts settle.
5. **N5 test-environment repair** whenever lockfile/dependency changes are explicitly approved; report blocked checks honestly.

Do **not** implement X2 delivery infrastructure, L1–L4, wallet/trade changes or speculative competitor copies in this run. If the full NOW scope exceeds one change set, prioritize N1 + N3, validate, and leave the remaining items as checked backlog rather than a broad untested patch.

## Definition of success for the phase

The NOW phase is complete only when a clean environment passes lint, unit/contracts, build and core Playwright tasks; all canonical destinations are consistent and deep-linkable; every shipped filter/refetch control changes real state truthfully; and the core find-trader → inspect → follow/watch journey works by touch and keyboard at 320 px and desktop widths.
