# Job 2 — UI/UX and Responsive Design Audit

**Run date:** 2026-08-16  
**Input:** Job 1 QC/QA report plus static review of the application shell, primary views, navigation, overlays, and global styles.  
**Method:** code-based heuristic review for mobile (320–430 px), tablet (768–1023 px), desktop (1024–1440+ px), keyboard, screen-reader, touch, and reduced-motion use. Dependencies are not installed, so this pass could not perform a rendered viewport or automated axe inspection. No product code was changed.

## Executive recommendation

**Do not optimize surface polish before repairing the navigation model and core control semantics.** The product exposes a large feature set, but its primary destinations change names across breakpoints, important controls are either unavailable or misleading on mobile, and several dense layouts assume more width than a 320–375 px device provides. First establish one URL-driven information architecture and semantic interaction model; then simplify high-frequency discovery/feed tasks; finally add progressive desktop density.

## Experience principles for the next implementation pass

1. **One destination, one label, one URL.** A view must not be “Feeds,” “Whales,” and `/feeds` depending on entry point.
2. **Mobile prioritizes the next decision.** Show market identity, risk/freshness, and one primary action before secondary statistics and tools.
3. **Progressive disclosure, not hidden functionality.** Advanced filters and long-tail tools belong in a clearly named More/Tools sheet, not in invisible breakpoint-only controls.
4. **Every apparent control works and communicates state.** Decorative chips, nested click targets, and non-semantic cards should not ship.
5. **Responsive means reflow, not horizontal-scroll discovery.** Horizontal scrolling is acceptable for data comparison only when it is labeled and has a visible affordance.

## Prioritized actionable findings

### P0 — Unify primary navigation and route-driven state before further UX work

- **Problem:** Bottom navigation labels `whales` as **Feeds** and `portfolio` as **Leaderboard**, while the desktop rail calls them **Whales** and **Portfolio**. Signals exists on desktop but is absent from mobile navigation. Job 1 also found that internal `setActiveTab` actions do not update URL/history, and `/whales` and `/portfolio` render Discover because route aliases re-export the forced root page.
- **Affected files:** `src/lib/moby-navigation.ts`, `src/app/page.tsx`, `src/app/whales/page.tsx`, `src/app/portfolio/page.tsx`, `src/components/moby/bottom-nav.tsx`, and every component that calls `setActiveTab` directly (including `discover-view.tsx`, `wallet-modal.tsx`, and profile quick links).
- **Mobile concern (320–430):** users cannot directly locate Signals; four bottom items offer inconsistent mental models, and transient tab changes leave the highlighted location wrong.
- **Tablet/desktop concern:** the rail promises Portfolio while opening Leaderboard content, increasing the cost of learning the product.
- **Recommendation:** define a route registry with canonical `label`, `shortLabel`, `href`, icon, and view. Choose either separate Portfolio and Leaderboard destinations or consistently name the combined destination (for example, **Portfolio** with a Leaderboard sub-tab). Add Signals to a five-item mobile nav if labels remain legible at 320 px, otherwise use four core destinations plus a clearly labeled **More** sheet. Make all navigation use links/router navigation; store state should derive from URL rather than compete with it.
- **Acceptance criteria:**
  - At `/`, `/feeds`, `/signals`, `/leaderboard` (or `/portfolio`), and `/profile`, URL, page title, heading, visible content, and `aria-current` agree.
  - Every navigation entry point supports Back, Forward, refresh, deep link, and open-in-new-tab.
  - The same destination uses the same user-facing name at 320, 768, 1024, and 1440 px.
  - All primary destinations are reachable on touch and keyboard at every breakpoint in at most two actions.

### P0 — Replace misleading/decorative controls with complete, accessible interactions

- **Problem:** Feeds filter chips look interactive but have no behavior; Reset announces success without changing state. Trader cards use a clickable `<div>` and contain a nested Follow button, creating ambiguous pointer/keyboard behavior. These are trust failures in a financial interface, not cosmetic defects.
- **Affected files:** `src/components/moby/feeds-view.tsx`, `src/components/moby/whales-view.tsx`, and similar clickable-card patterns identified by a repository-wide semantic audit.
- **Viewport concern:** at narrow widths the chip row wraps around an icon and a tiny “Hide” link, producing an unstable control block; Follow consumes scarce card width and can force trader identity truncation.
- **Recommendation:** implement filters as a compact **Filters (n)** button opening a bottom sheet on mobile and a popover/side panel on larger screens. Keep one or two high-frequency quick filters visible only if functional. Render the trader title as a semantic link/button, keep Follow as a separate sibling action, and ensure the entire card is not a nested interactive target.
- **Acceptance criteria:**
  - Filter trigger exposes `aria-expanded`, active count, selected values, Apply/Clear behavior, and changed results.
  - Reset/Clear is disabled at defaults and never reports success without a state change.
  - Trader detail and Follow are separately reachable by Tab, have visible focus, and activate with Enter/Space without triggering each other.
  - All primary touch targets are at least 44×44 CSS px or have equivalent spacing; no reliance on 11 px text as the only tap target.

### P1 — Redesign the top bar for narrow phones and eliminate duplicate search state

- **Problem:** the top bar simultaneously fits logo, chain selector, flexible search input, alerts, and wallet; additional tools appear at `sm`. At 320 px this creates severe competition for width. The visible search input also owns a query that is disconnected from the SearchModal query (Job 1), so users type twice or see inconsistent clearing.
- **Affected files:** `src/components/moby/top-bar.tsx`, `src/components/moby/search-modal.tsx`, `src/lib/moby-store.ts` (if shared query state is selected).
- **Mobile concern (320–374):** chain label + search + two actions can compress the search to an unusable width; the clear button is only `h-3 w-3`, far below a touch target. Wallet labeling may further crowd the row.
- **Recommendation:** on phones use a logo/home button, compact chain icon, icon search trigger, notifications, and compact wallet/avatar. Let search open one full-width command sheet with one controlled query and autofocus. At ≥768 px, expose the inline controlled search field. Move screener, tax, and AI into an explicit Tools/More surface rather than relying only on `hidden sm:*` behavior.
- **Acceptance criteria:**
  - At 320 px with 200% text zoom, header controls neither overlap nor create horizontal page overflow.
  - One query drives trigger and modal; type, clear, Escape, close, and reopen are deterministic.
  - Search trigger and clear action have accessible names and ≥44×44 px hit areas.
  - All hidden phone tools are reachable through a named menu in two actions or fewer.

### P1 — Reflow dense three- and four-column mobile data instead of shrinking it

- **Problem:** trader cards use four equal statistic columns, live-flow content uses a three-column grid with a 46 px left indent, and DCA/Profile quick actions use three/four fixed columns. At 320–375 px this yields very narrow cells, tiny labels, awkward wrapping, and poor scan order.
- **Affected files:** `src/components/moby/whales-view.tsx` (notably trader stats and flow stats), `src/components/moby/feeds-view.tsx` (DCA actions), `src/components/moby/profile-view.tsx`, `src/components/moby/discover-view.tsx` and other fixed `grid-cols-3/4` sections.
- **Recommendation:** default to two columns on narrow mobile and promote only the two decision-critical metrics (for traders: Smart score and 30d PnL). Put win rate/ROI in an expandable details region or second row. Use `sm:grid-cols-*`/`lg:grid-cols-*` to increase density. For quick actions, use a two-column grid or vertical list with icon, label, and short description.
- **Acceptance criteria:**
  - At 320×568 and 375×667, labels do not collide, truncate critical numbers, or require page-level horizontal scrolling.
  - At 200% zoom, content reflows without loss of controls or values.
  - Reading order in DOM matches visual order; values remain associated with labels for screen readers.
  - Tablet and desktop gain density without duplicating content or changing task order.

### P1 — Make horizontal tabs discoverable and semantically correct

- **Problem:** nested Feeds tabs and Whales sub-tabs create two levels of local navigation. Whales uses `overflow-x-auto no-scrollbar`, hiding any evidence that more tabs exist. “Trenches” opens a modal instead of selecting a tab, violating the tab pattern.
- **Affected files:** `src/components/moby/feeds-view.tsx`, `src/components/moby/whales-view.tsx`, `src/components/moby/signals-view.tsx`, and other horizontal chip/tab groups in `discover-view.tsx`.
- **Viewport concern:** four Whales labels are unlikely to fit at 320 px; no scrollbar, fade, partial next item, or “More” clue indicates overflow.
- **Recommendation:** reduce nesting: make Whale Watch, Movers, and DCA the route/view tabs; within Whale Watch use a segmented control for Top Traders / Live Flows / Smart Money. Move Trenches to Tools or label it as an action rather than a tab. Use Radix Tabs semantics or equivalent (`tablist`, `tab`, `tabpanel`, arrow-key behavior). If scrolling remains, expose an end fade and scroll the active tab into view.
- **Acceptance criteria:**
  - Tab controls expose selected state and correct relationships to panels; Left/Right arrow changes focus/selection.
  - Actions that open overlays are styled/labeled as actions, not tabs.
  - At 320 px every option is discoverable without an invisible horizontal-scroll requirement.
  - Selected sub-view persists through refresh/deep link when it materially changes the task.

### P1 — Establish a consistent responsive overlay pattern with focus and safe-area handling

- **Problem:** overlays independently implement fixed positioning and sizing: search starts at `10vh`, wallet/trade are bottom sheets, notifications are full-height, and token detail is `h-[88vh]`. This risks keyboard obstruction, clipped content, inconsistent close behavior, and missing safe-area padding. Job 1 identified the need for focus-trap and Escape-order coverage across many simultaneously mounted modals.
- **Affected files:** `src/components/moby/search-modal.tsx`, `wallet-modal.tsx`, `trade-modal.tsx`, `discover-view.tsx` detail overlay, the many modal components mounted in `src/app/page.tsx`, and reusable `src/components/ui/dialog.tsx` / `drawer.tsx` / `sheet.tsx`.
- **Mobile concern:** `vh` can behave poorly with browser chrome and the virtual keyboard; bottom actions may sit behind the iOS home indicator.
- **Recommendation:** standardize on accessible Dialog for centered desktop overlays and Drawer/Sheet for mobile, using `100dvh`, scrollable body, sticky header/footer, `env(safe-area-inset-*)`, focus trap, focus return, background inertness, and one overlay stack manager. Search should begin directly below safe top inset, not an arbitrary 10vh gap.
- **Acceptance criteria:**
  - At 320×568 and 390×844, with the keyboard open, focused fields and primary actions remain visible and scrollable.
  - Opening moves focus inside; Tab is trapped; Escape closes only the top overlay; closing returns focus to its trigger.
  - Content is not hidden by notches/home indicators and respects landscape safe areas.
  - Screen readers receive an accessible dialog name and description; background content is not traversable.

### P1 — Distinguish loading, error, empty, filtered-empty, stale, and offline states

- **Problem:** Discover labels upstream failure as “No tokens match your filters,” and refresh may shuffle local data instead of refetching. A trading product must communicate provenance and freshness clearly.
- **Affected files:** `src/components/moby/discover-view.tsx`, `src/components/moby/whales-view.tsx`, `src/hooks/use-gmgn.ts`, and shared status components such as `src/components/ui/staleness-badge.tsx`.
- **Responsive concern:** verbose raw errors should not dominate small screens, but hiding state is unsafe. Status should be concise with expandable detail.
- **Recommendation:** use a shared status pattern: skeleton for initial load; inline stale banner while preserving data; error banner with Retry; true empty-state guidance; filtered-empty with Clear filters; offline badge. Announce changes through a restrained `aria-live` region, not toast-only feedback.
- **Acceptance criteria:**
  - Each state has distinct copy, icon/status, next action, and automated component coverage.
  - Refresh preserves existing content, shows progress, updates a visible freshness timestamp, and announces completion/failure.
  - State messaging fits 320 px without horizontal overflow and remains understandable without color.

### P2 — Simplify the first-run and daily workflow around user intent

- **Problem:** the shell mounts dozens of feature modals while the home/feed surfaces expose many carousels and quick actions. The product lacks a clear “what should I do next?” path, and broad feature visibility competes with the core whale-tracking value proposition.
- **Affected files:** `src/app/page.tsx`, `src/components/moby/onboarding.tsx`, `discover-view.tsx`, `profile-view.tsx`, and feature-launch controls throughout Moby components.
- **Recommendation:** make onboarding intent-based: (1) choose chain, (2) optionally connect or watch a wallet, (3) select interests/risk, (4) land on a populated watch feed. For returning users prioritize **Watchlist / Whale activity / Signals**, then defer scanners, tax, bridge, staking, and experimental tools to a searchable Tools catalog. Do not require wallet connection merely to browse.
- **Acceptance criteria:**
  - A new user can reach relevant whale activity in ≤3 decisions and can skip onboarding.
  - A returning user can inspect an alert and act/watch in ≤3 actions from launch.
  - Advanced features remain searchable and reachable but do not compete with the primary CTA above the fold at 320×568.
  - Onboarding progress, Back, Skip, and resume behavior are keyboard/screen-reader accessible.

### P2 — Add reduced-motion, contrast, zoom, and non-color requirements

- **Problem:** global styles define marquee, live pulse, price flashes, motion transitions, and Framer Motion page changes but no `prefers-reduced-motion` handling was found. Several labels use 9–11 px text and muted colors, while bull/bear color carries meaning.
- **Affected files:** `src/app/globals.css`, `src/app/page.tsx`, `src/components/moby/bottom-nav.tsx`, motion-heavy cards/modals, and primitive badge/status components.
- **Recommendation:** disable non-essential marquee/pulse/translation/flash motion under reduced motion; use symbols and signed values alongside color; set a practical 12 px floor for secondary UI text and 14–16 px for controls/body copy; test both themes against WCAG 2.2 AA. Avoid suppressing browser zoom.
- **Acceptance criteria:**
  - `prefers-reduced-motion: reduce` removes continuous motion and spatial page transitions without removing status information.
  - Normal text meets 4.5:1 contrast and large/UI graphics meet applicable 3:1 contrast in dark and light themes.
  - Gains/losses, live/stale, selected/unselected, and errors are understandable in grayscale.
  - Browser zoom at 200% and text spacing overrides do not clip or hide content/actions.

### P2 — Improve desktop use of space without creating a second product

- **Problem:** at ≥1024 px, a 260–320 px workspace rail sits beside one large app column. The rail contains explanatory/status cards while dense feed content remains a single mobile-style stream, leaving comparison and monitoring potential unused.
- **Affected files:** `src/app/globals.css`, `src/app/page.tsx` (`DesktopRail` and shell), primary views.
- **Recommendation:** retain one responsive component tree, but at ≥1200 px allow a two-pane workspace: results/feed on the left and selected token/trader details on the right. Keep the rail compact/collapsible. Do not merely scale mobile cards wider; cap readable text width and use additional columns for comparable data.
- **Acceptance criteria:**
  - At 1024 px the app has no horizontal overflow and the main task has adequate width.
  - At 1440 px a selected result can remain visible alongside details, with keyboard focus and URL state preserved.
  - No essential action exists only on hover; all desktop actions work by keyboard and touch-capable laptop input.

## Recommended simplified flows

### Flow A — Find and follow smart money

1. Open **Whale activity** (canonical destination).
2. Default to **Top traders**, with compact Sort and Filters controls showing active state.
3. Open trader detail as a route-backed sheet/pane.
4. Follow from the detail header; confirm inline and offer **Create alert** as the next optional action.

**Target:** trader detail in ≤2 actions; follow in ≤3; Back returns to the same sorted position.

### Flow B — Investigate an alert

1. Open Alerts from header/badge.
2. Select alert; land in a route-backed token/trader detail with source and timestamp.
3. Present one primary context-sensitive action (Watch/Follow) and a secondary **Trade** action only when safe/available.

**Target:** no duplicate modal chain, no lost scroll/filter state, and one Escape/Back level per conceptual step.

### Flow C — Search once, act once

1. Open Search; one field searches token, symbol, contract, trader, or wallet.
2. Group results by type with recent searches before input.
3. Selecting a result opens a route-backed detail; query remains when returning.

**Target:** type only once; first useful result keyboard-selectable; clear and close behavior consistent.

### Flow D — Configure a feed

1. Open Filters (active count visible).
2. Choose transaction type, wallet class, timeframe, and sort in a single sheet/panel.
3. Preview result count, Apply, and retain a visible removable-filter summary.

**Target:** defaults useful without configuration; Clear All available only when applicable; zero results offers one-click recovery.

## Responsive validation matrix

| Viewport | Required review |
|---|---|
| 320×568 | smallest supported phone, header crowding, 200% zoom, modal keyboard, two-column reflow |
| 375×667 | common narrow phone, fixed navigation, tab/filter discoverability, touch targets |
| 390×844 / 430×932 | modern iPhone safe areas, long content, bottom sheets and sticky actions |
| 844×390 | phone landscape, safe-area sides, keyboard and overlay height |
| 768×1024 | tablet portrait, avoid stretched phone UI, navigation transition |
| 1024×768 | tablet/desktop breakpoint boundary and rail width |
| 1280×800 / 1440×900 | desktop density, two-pane opportunity, focus order |

For every viewport assert: no document-level horizontal overflow, no obscured focus, all controls reachable, sticky elements do not cover content, 44 px touch targets, visible focus, correct heading hierarchy, status independent of color, and usable 200% zoom.

## Implementation sequence handed to Job 4

1. **Foundation:** canonical route registry; route-backed navigation/sub-views; consistent names; repair aliases.
2. **Semantics and trust:** functional filters/reset/refresh; semantic cards; distinct async states; stable accessibility names.
3. **Mobile shell:** compact top bar, discoverable More/Tools, five-item-or-four-plus-More nav decision, safe-area/dynamic viewport overlay primitive.
4. **Responsive content:** reflow fixed grids, simplify trader/feed cards, disclose secondary metrics, visible overflow affordances.
5. **Accessibility hardening:** focus traps/return, keyboard tabs, reduced motion, contrast, 200% zoom, axe tests.
6. **Desktop enhancement:** compact rail and route-backed list/detail pane only after mobile workflows pass.

## Validation required after implementation

- Playwright route/task tests across the viewport matrix, including Back/Forward, reload, landscape, and virtual-keyboard scenarios.
- Automated axe checks on each canonical route and every shared overlay state; manual VoiceOver/TalkBack plus keyboard-only pass.
- Visual regression for dark/light themes, long translated labels, large numbers, empty/error/stale states, and 200% zoom.
- Performance check on a mid-tier mobile profile: overlays/features should load on demand and interaction should remain responsive during feed updates.
